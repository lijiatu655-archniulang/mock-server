# 设计思路与版本功能清单 · 新源村情通

> 本文回答两个问题：**为什么这样设计**（而不是照抄原型），以及**每个版本到底交付哪些功能**。
> 与其它文档的关系：`00` 讲产品定位与比赛材料，`01` 讲后端架构，`03` 讲接口契约；**本文讲设计推理与交付清单**，是给「两个人 + 两个 AI」看的作战地图。

---

## 0. 一页看懂

**一句话定义**：把村务公开、政务办事、群众诉求装进一个微信小程序，再配一个懂本地政策、能指路的 AI 网格员。

**三层价值**

| 层 | 对谁 | 价值 |
|---|---|---|
| 看得见 | 村民 | 村里的事、上面的政策，一个屏看完 |
| 问得着 | 村民（尤其老人） | 不用找人、不用等回复，AI 说人话、给出处 |
| 办得成 | 村民 + 网格员 | 养老/医保缴费、独生子女证、出生证明，线上申报、进度可查 |

**四个版本一句话**

| 版本 | 一句话 | 关键词 |
|---|---|---|
| V1 | 能看、能问 | 底座、内容、AI |
| V2 | 能办 | 政务闭环、六大入口 |
| V3 | 能管 | 网格员工作台、数据、Agent |
| V4 | 能运营 | 增长、上线、打磨 |

## 1. 设计起点：从三张截图里读出什么

### 1.1 界面元素还原

| 界面元素（原型） | 用户真正的意图 | 产品含义 | 我们的处理 |
|---|---|---|---|
| 顶部红底 + 党徽 + 「中共新源县委组织部」 | 「这是官方的，可信」 | 信任背书是一等需求 | 保留，且页脚固定展示主办/举报/备案 |
| 村名下拉 + 「查看全部」 | 「我只看我们村」 | 多村可复制 | `sys_region` 四级树，接口按 `regionId` 过滤 |
| 四个胶囊：村情动态/三务公开/乡风纪实/政策速递 | 「我想分类看」 | 栏目要能增删 | `cms_column` 配置化，前端不写死四个 |
| 资讯流（标题 + 时间） | 「最近发生了什么」 | 内容做留存钩子 | 置顶 + 时间倒序 + 详情页富文本 |
| 九宫格六个入口 | 「我要办事」 | **真正的入口价值** | `app_module` 配置化 + V2 逐个接业务 |
| 页脚：主办/举报/备案 | 「这是正规的」 | 合规信息 | `sys_config` 下发，改文案不发版 |
| AI 页：欢迎语 + 气泡 + 免责声明 | 「我问了它能答吗」 | 可信 + 低门槛 | 推荐问题、引用来源、固定免责、可停止生成 |
| 个人中心：姓名 + 三级网格标签 | 「我是谁、归谁管」 | 身份决定能办什么 | `regionPath` 数组，角色进 token |
| 底部 Tab：首页 / AI 网格员 / 个人中心 | 「三个地方够用」 | 不做第四个 Tab | 服务入口收进九宫格 |

### 1.2 原型给我们的三个「机会点」

不是挑毛病，是找增量——**复刻界面只能拿及格分，补上闭环才有区分度**。

1. **内容有了，但只能「看」。** 政策长文老人读不懂 → 加「问」：AI 网格员，答案带出处。
2. **入口有了，但点进去是空的。** 六个格子如果都是「敬请期待」，评委一眼看穿 → 加「办」：先把**政务管理**做成真能办的四类事项。
3. **身份有了（网格员），但没有「工作台」。** 网格员登录后和村民看到的一样 → 加「管」：V3 做待办、走访、事件上报。

> 这三条就是 V1→V3 的主线：**看 → 问 → 办 → 管**，每一版补一个闭环。

### 1.3 我们刻意不改的东西

- **红底 + 党徽 + 主办单位**：这是政务产品的「信任视觉」，改了反而假。
- **三 Tab**：不为了显得功能多而加 Tab；入口收进九宫格，符合「一个屏解决」的小程序心智。
- **胶囊式栏目**：比 `uni-segmented-control` 更有辨识度，且能横向扩展。

## 2. 用户与场景推演

### 2.1 三类人 × 三个时刻

| 用户 | 时刻 | 场景 | 我们要保证的体验 |
|---|---|---|---|
| 村民（55 岁，务农） | 早上 8 点 | 刷一眼村里有没有通知 | 首屏 1 次请求、3 秒内可见 |
| 村民（32 岁，外出务工） | 晚上 9 点 | 帮父母交医保、问政策 | 代办入口明显、支付/代收都能走通 |
| 网格员（兼职） | 随时 | 有人问「我这个能不能办」 | 一句话能转发给村民；后台能受理 |
| 乡镇/组织部 | 月底 | 看各村活跃度 | V3 数据看板（活跃、办件、满意度） |

### 2.2 关键洞察：这是一个「代际代办」产品

真实村庄里，**会用小程序的人和要办事的人往往不是同一个人**。这条洞察直接改变了设计：

- 办件表必须有 `agent_user_id`（代办人），日志要区分「本人提交」与「代提交」；
- 「我的办件」要能按**家庭成员**看（V3），而不只是自己；
- 缴费金额必须由后端核定（代办场景更容易被改金额）；
- 订阅消息要发给**申请人**，不是代办人。

> 如果只按「一个用户 = 一个人」设计，这个产品在村里跑不起来。这是我们从原型之外补的第一条产品判断。

### 2.3 任务优先级（按频率 × 刚性）

```text
高频 ────────────────────────────────
  │  ① 办事（缴费/证明）      ← 刚性最强，一年至少 2 次，漏了有后果
  │  ② 问政策（"我这情况能不能办"）  ← 高频、低门槛
  │  ③ 看资讯（通知/活动）    ← 高频、低刚性
  │  ④ 诉求（纠纷/报修）      ← 低频、高情绪
  │  ⑤ 管理（网格员）         ← 低频、强需求（B 端）
低频 ────────────────────────────────
```

结论：**V1 先把 ②③ 做扎实（因为技术风险最低、演示效果最好），V2 攻 ①，V3 补 ④⑤。**

## 3. 产品结构怎么长出来的

### 3.1 信息架构

```text
TabBar（3 个，不加第 4 个）
├── 首页
│   ├── 信任区：红底 + 村名 + 主办单位
│   ├── 内容区：4 栏目胶囊 + 资讯流
│   ├── 服务区：九宫格（咨询帮办/诉求建议/线上奶茶会
│   │                    服务黄页/政务管理/就业招聘）
│   └── 合规区：主办 · 举报渠道 · 备案号
├── AI 网格员（新源小智）
│   ├── 推荐问 → 流式回答 → 引用来源 → 赞/踩
│   └── 历史会话 + 免责声明
└── 个人中心
    ├── 身份卡（姓名/角色/三级网格）
    ├── 我的办件（V2）/ 我的诉求（V2）
    └── 在线客服 / 退出
```

### 3.2 为什么是「九宫格」而不是更多 Tab

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 每个业务一个 Tab | 直达 | Tab 最多 5 个，且业务会变 | ❌ |
| 首页做成「服务大厅」长列表 | 扩展性好 | 首屏变长，资讯被挤走 | ❌ |
| **九宫格 + 配置化路由** | 一屏放下、可下线、可运营（角标） | 需要后端配置 | ✅ 采用 |

关键：九宫格的数据来自 `app_module` 表，**上线节奏由后端 `status` + `features` 开关控制**，前端不用发版就能「开一个入口」。

### 3.3 一个入口，三层角色

同一个页面，按角色渲染不同能力（V1 只做村民，V3 补网格员）：

| 能力 | 村民 | 网格员 | 乡镇/管理员 |
|---|---|---|---|
| 看内容 | ✅ | ✅ | ✅ |
| 问 AI | ✅ | ✅ | ✅ |
| 办事项 | 自己办 / 找人代办 | 代村民办 | 受理、核准 |
| 诉求 | 提交 | 受理、办结 | 督办、统计 |
| 数据 | — | 本网格 | 全村/全镇 |

## 4. 关键设计决策（ADR）

> 每条都写「代价」和「什么时候该反悔」，避免把临时决定当成信仰。

### ADR-01 模块化单体，不拆微服务

- **背景**：两人开发、5 天出 V1、单人可维护。
- **决策**：单 Spring Boot 应用，按业务垂直分包（`modules/gov`、`modules/ai`…）。
- **代价**：无法独立扩缩容；模块间可能偷偷互相调用。
- **反悔条件**：单模块 QPS 超过单机承载（如 AI 流式占满线程池），再拆 AI 为独立服务。
- **为什么写进答辩**：评委更认「按业务边界分包、能演进」而不是「堆组件」。

### ADR-02 首页做一个聚合接口，而不是六个并行请求

- **背景**：小程序首屏白屏时间是体验生死线；弱网（村里 4G）更差。
- **决策**：`GET /home` 一次返回 banner + 栏目 + 资讯 + 九宫格 + 页脚，Redis 缓存 60s。
- **代价**：接口耦合、改字段要一起改；缓存一致性要处理。
- **反悔条件**：首页出现强个性化（千人千面）时，拆成「骨架 + 分片」。
- **收益**：首屏 1 次往返；评测现场不易打爆数据库。

### ADR-03 一切可配置：栏目、入口、事项表单

- **背景**：村务内容天天变；如果每个入口、每个表单都写死，改一次要发版 + 审核。
- **决策**：
  - 栏目 → `cms_column`；
  - 九宫格 → `app_module`（含 `route`、`badge`、`status`）；
  - 政务事项 → `biz_service_item.form_schema`（JSON 动态表单）；
  - 页脚/举报/备案 → `sys_config`。
- **代价**：后台要能维护；JSON 表单需要前端渲染器。
- **反悔条件**：事项超过 30 个、表单出现复杂联动时，引入低代码表单引擎。

### ADR-04 AI 先结构化、再 RAG、最后兜底

- **背景**：纯 RAG 会「一本正经胡说」，而政策金额/时限错了是事故。
- **决策**：三级回答链路
  1. 办事类问题 → 先查 `biz_service_item`（材料/时限/金额是权威数据）；
  2. 政策类问题 → MySQL ngram 全文 + 关键词加权召回知识切片；
  3. 都没命中 → 明确说「没查到，建议联系村委会/12380」，**不编**。
- **代价**：要维护两套数据（事项表 + 知识库），有重复。
- **反悔条件**：知识库规模上千条、语义检索需求明显时，升级向量检索（V3）。

### ADR-05 政务 V1 只读、V2 闭环

- **背景**：5 天做不完「申报 + 支付 + 受理 + 出证」；但九宫格点进去是空白页会很掉分。
- **决策**：V1 交付事项/材料/流程/动态表单（只读），接口与表结构**当场冻结**；V2 只加实现，不改契约。
- **代价**：V1 的演示少一个「办成」的高光时刻。
- **反悔条件**：如果省赛前多出 2 天，优先把「独生子女证申报」跑通（不接支付，最容易闭环）。

### ADR-06 用 mock-login 换并行开发

- **背景**：前端没有小程序 appid、后端没配微信密钥时，两边都卡住。
- **决策**：`dev` profile 提供 `POST /auth/mock-login`，直接发种子用户的真 token。
- **代价**：多一个只在开发环境存在的接口（prod 返回 404）。
- **收益**：前端不必等后端、后端不必等微信审核，**这是两个人五天真能并行的前提**。

### ADR-07 小程序端手写 SSE 解析

- **背景**：小程序没有 `EventSource`，但「逐字输出」是 AI 体验的分水岭。
- **决策**：`wx.request({ enableChunked: true })` + `onChunkReceived` + 自写事件解析（`meta/delta/refs/done/error`）。
- **代价**：要处理粘包/半包、真机与工具差异、Nginx 缓冲。
- **反悔条件**：微信官方 SSE 支持稳定后，换官方能力。

### ADR-08 契约冻结，只增不改

- **背景**：两个 AI 各自写代码，最容易死在「字段悄悄改名」。
- **决策**：`/api/v1` 路径、`Result` 结构、枚举值一经发布只增不改；破坏性变更开 `/api/v2`。
- **代价**：偶尔要背历史包袱（如保留废弃字段一个版本）。
- **收益**：V2/V3 几乎不因接口吵架，返工率最低。

## 5. 数据模型的推导

### 5.1 从界面反推表

| 界面上看到的 | 必须有这张表 | 关键字段 |
|---|---|---|
| 村名、所属网格三级标签 | `sys_region` | `parent_id`、`level_code`、`path` |
| 头像、姓名、角色、手机号 | `sys_user` | `openid`、`role_code`、`region_id`、`grid_id` |
| 四个栏目胶囊 | `cms_column` | `code`、`sort_no` |
| 资讯流 + 详情 | `cms_article` | `column_id`、`is_top`、`status`、`content` |
| 轮播图 | `cms_banner` | `link_type`、`link_value` |
| 九宫格 | `app_module` | `route`、`badge`、`status` |
| 页脚 / 免责声明 | `sys_config` | `config_key`、`config_value` |
| AI 对话、历史会话 | `ai_conversation` / `ai_message` | `refs`、`feedback`、`latency_ms` |
| AI 回答的「依据」 | `ai_kb_document` / `ai_kb_chunk` | `content`、`keywords`、`FULLTEXT ngram` |
| AI 的人设与风格 | `ai_prompt_template` | `scene`、`version` |
| 政务四类事项 + 材料 | `biz_service_item` / `biz_service_material` | `form_schema`、`required` |
| 办件、附件、进度 | `biz_service_apply` / `_file` / `_log` | `status`、`apply_no`、`agent_user_id` |
| 图片/材料上传 | `sys_file` | `biz_type`、`url` |
| 用户行为、后台操作 | `sys_event_log` / `sys_audit_log` | `event_code`、`module` |

**22 张表，没有一张是「为了架构好看」加的**——每张都能指回界面上一个元素或一条业务规则。

### 5.2 三个建模取舍

1. **事项表单用 JSON 还是拆表？** 用 JSON（`form_schema`）。
   - 理由：表单字段随政策变，拆表要改 DDL；JSON 让「后台建事项零代码」成立。
   - 代价：不能按字段查库（但我们不需要按表单字段检索）。
2. **办件要不要冗余 `item_name`？** 要。
   - 理由：事项改名/下线后，历史办件必须还能正确显示「我当时办的是什么」——快照字段是审计要求。
3. **逻辑删除 vs 物理删除？** 内容、办件用逻辑删除（`deleted`）；会话消息 180 天后物理清理（个人信息最小化）。
   - 代价：所有查询必须带 `deleted=0`（在 Mapper 里统一拼，别靠人记）。

## 6. 交互与视觉思路

### 6.1 视觉锚点

| 元素 | 规格 | 理由 |
|---|---|---|
| 主红 `#C4161C` | 导航、按钮、TabBar 选中 | 政务感、与原型一致 |
| 顶部深红 `#8E0F14` | 头部渐变 | 让白色标题字更稳 |
| 暖橙 `#E8641B` | 「村情动态」胶囊渐变 | 与红色区分栏目，避免一屏全红 |
| 卡片圆角 12rpx / 胶囊 999rpx | — | 柔和，不廉价 |
| 正文字号 30rpx / 标题 34rpx | — | 60 岁用户可读 |

### 6.2 老年友好（不是口号，是具体规则）

- 一屏一个主动作（首页 = 看资讯；AI 页 = 输入框；政务页 = 下一步）；
- 点击区域 ≥ 88rpx（手指粗、有老花）；
- 不用纯图标导航，图标必须带文字；
- 表单字段一行一个，不用两列排版；
- 错误提示写「怎么办」，不写「参数错误」。

### 6.3 状态设计（四态齐全才算做完）

每个列表/详情页必须有：**加载中（骨架屏）· 空（有引导动作）· 错误（可重试）· 无权限（引导登录）**。
> 这是评审「完成度」最容易扣分的地方，也是前端 AI 最容易漏的地方。

### 6.4 AI 的「可信感」设计

| 设计 | 目的 |
|---|---|
| 回答附「依据：XX 政策」 | 让村民可核对，不是黑箱 |
| 固定免责声明（每屏可见） | 合规，也降低「答错」的预期 |
| 推荐问题气泡 | 解决「不知道怎么问」 |
| 停止生成按钮 | 给用户控制感 |
| 兜底话术（没查到就直说） | 不胡说 > 答得多 |
| 赞/踩 | 收集知识盲区，形成运营闭环 |

## 7. 版本划分的逻辑

### 7.1 按「闭环」分，不按「页面」分

如果按页面分版本（这版做 5 个页面、下版做 6 个），会出现「每版都半成品」。我们按**闭环**分：

| 版本 | 闭环 | 判断「做完了」的标准 |
|---|---|---|
| V1 | **读闭环**：内容能看、AI 能答 | 新用户进来 30 秒内能看懂这是什么、能问出第一个问题 |
| V2 | **写闭环**：事能办、诉求能提 | 一个办件从提交到评价走完，中途不靠人工干预 |
| V3 | **治理闭环**：网格员能管、数据能看 | 网格员一天的工作能在小程序里完成并留痕 |
| V4 | **运营闭环**：能拉新、能留存、能上线 | 有分享路径、有数据看板、过审上线 |

### 7.2 每个版本必须同时满足三条

1. **可独立演示**（不依赖下一版的功能才能讲通）；
2. **不推翻上一版契约**（只加字段/接口，不改语义）；
3. **有可量化验收**（见第 8 节每版的「验收」列）。

### 7.3 依赖关系

```text
V1 底座 ──(契约冻结)──> V2 政务闭环 ──> V3 治理 ──> V4 运营
   │                        │                │
   ├ 内容/组织/配置 ────────┼────────────────┤
   ├ AI 会话/RAG ───────────┼──> 意图识别 ────┼──> Agent 工具
   └ 政务只读 ──────────────┴──> 申报/缴费 ───┴──> 代办/OCR/证照
```

**关键约束**：V2 的申报接口依赖 V1 的 `form_schema` 与材料表；V3 的 Agent 依赖 V2 的办件数据。所以 **V1 的数据模型必须一次设计对**（这也是为什么 V1 就建了政务 5 张表，哪怕只读）。

## 9. 跨版本契约不变式

这四条写死，任何版本都不许破：

1. **路径不改**：`/api/v1/...` 一旦发布，只新增，不重命名。
2. **响应体不改**：`{code,message,data,traceId,timestamp}` 永远这套壳。
3. **枚举只增**：`applyStatus` 可以加新状态，不改旧值含义；前端遇到未知值要能兜底显示。
4. **表只加字段**：不删列、不改列语义；废弃字段保留一个版本并标注 `@Deprecated`。

> 为什么值得强调：两个 AI 并行时，90% 的返工来自「字段改名」「枚举含义变了」。这四条能省掉大量联调时间。

## 12. 答辩叙事线（3 分钟版）

1. **痛点（20s）**：一个村 1 个网格员服务几百户；政策靠大喇叭，办事靠跑腿，老人跑不动、子女回不来。
2. **产品（30s）**：一个入口三层角色——村民看与问、网格员办与记、乡镇看与管。首页截屏对比原型：一样的壳，多了「政务管理」。
3. **AI（50s）**：不是聊天机器人。**先查结构化事项表，再查知识库，查不到就说不知道**；回答带出处；点踩的提问进「知识盲区」，网格员一键补知识——AI 越用越准。
4. **闭环（40s）**：现场演示一个办件：选事项 → 材料清单 → 提交 → 受理 → 办结 → 评价（V2 录屏）。
5. **工程（30s）**：Spring Boot + MyBatis + MySQL；小程序 SSE 流式（`enableChunked` 手写解析）；契约冻结，两人两 AI 并行。
6. **落地（10s）**：一个村试点 → 全镇 8 村复制 → 县域 SaaS，换村名换知识库即可。
